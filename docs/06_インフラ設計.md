## 2. ネットワーク構成

## 3. CI/CD

### 3.1 GitHub Actions（`github`リモート）

`.github/workflows/test.yml`を新規作成し、push・pull_request時に自動でpytestを実行する。

- トリガー: `main`ブランチへのpush、`main`向けのpull_request
- 実行環境: `ubuntu-latest`
- Python: 3.11（現行コードは`CLAUDE.md`のコーディング指針により、JV-Link接続部分を除き環境非依存で実装されているため、Windows専用ランナーは現時点で不要）
- 手順: リポジトリのチェックアウト → Python セットアップ → 依存関係インストール（`pip install -e ".[dev]"`）→ `pytest -q`

**今後の注意**: `JVLinkDataSource`（Windows専用・pywin32依存）を実装した際は、そのモジュールをデフォルトのCI実行対象から除外するか、Windows専用ジョブを別途追加する必要がある。現時点では対象モジュールが存在しないため対応不要。

このワークフローは`github`リモート（GitHub Actions）へのpush時にのみ実行される。`origin`（Backlog）へのpushではGitHub Actionsは動作しない。

### 3.2 Backlog側CI/CDの調査結果と方針

Backlog自体には、GitHub Actionsのようなリポジトリ内蔵のパイプライン実行機能（YAMLベースの自動実行）は提供されていない。調査した結果、以下の選択肢がある。

| 選択肢 | 概要 | 備考 |
|---|---|---|
| Jenkins連携 | Nulab公式が案内する構成。BacklogのGit webhookでJenkinsジョブを起動 | 別途Jenkinsサーバーの構築・運用が必要。個人利用にはオーバースペック |
| AWS CodePipeline/CodeBuild連携 | BacklogのGit webhookからAWS側のパイプラインを起動 | AWSアカウント・費用が発生。同様にオーバースペック |
| QuickOps（サードパーティ） | Backlog Git専用のCI/CDサービスとして提供されていた | **新規受付終了済み**のため現在は利用不可 |

**方針**: 個人利用・非商用の本プロジェクトの規模では、上記いずれも構築・運用コストが見合わない。**当面はGitHub Actionsのみで自動テストを運用し、Backlog（origin）側は手動での`pytest`実行を継続する**。両リモートには同一のコミットをpushしているため、GitHub Actions側のテスト結果を実質的な唯一のCI結果として扱う。

この方針は将来変更の余地がある（要件定義書12章に準ずるオープン課題として扱う）。Jenkins等の構築が必要になった場合は、別途要件定義・設計を行う。

## 4. 設定管理設計

要件定義書§5（セキュリティ）に「認証情報は環境変数または設定ファイルで管理する」とあるが、設定ファイルの形式・置き場所や、認証情報以外の設定値の扱いはこれまで未設計だった。以下の方針とする。

| 設定値の種類 | 具体例 | 管理方法 |
|---|---|---|
| 秘匿情報 | `JVLINK_MEMBER_ID`, `JVLINK_PASSWORD` | 環境変数、または`.env`ファイル（`.gitignore`対象）。詳細は`07_セキュリティ設計.md`§1 |
| 非秘匿の設定値 | DBファイルパス（例: `data/keiba.db`） | 専用の設定ファイルは導入せず、CLI引数のデフォルト値で管理する（例: 将来`--db-path`引数を追加し、デフォルト`data/keiba.db`） |

**設計判断**: Phase 1時点で外部化が必要な非秘匿設定値はDBパス程度であり、これはCLI引数のデフォルト値で十分に管理できる。そのため、YAML/TOML等の専用設定ファイル（`config.toml`等）は現時点では導入しない。設定項目が増えた場合（例: JV-Link接続先の詳細設定、複数DB切り替え等）は、`pyproject.toml`に`[tool.keiba]`セクションを追加するか、別途`config.toml`を導入することを検討する。

## 5. ログ設計

現状、すべての出力は`print()`による標準出力のみであり、ログファイルへの出力・ログレベル（DEBUG/INFO/WARNING/ERROR）の使い分けは行っていない。

**方針**: 個人利用・都度手動実行というスコープでは、標準出力の確認で運用上支障が無いため、Phase 1では現状を維持する。将来、定期実行（バッチ化）やエラー調査の必要性が生じた場合は、Python標準の`logging`モジュールを導入し、`data/logs/`配下（`.gitignore`対象）にログファイルを出力する設計に拡張する。優先度は低（要件定義書12.4相当の保留事項として扱う）。

## 6. バックアップ・データ保持方針

SQLiteファイル（`data/*.db`）はローカルPC 1台にのみ存在し、自動バックアップの仕組みは提供しない。

- **リスク**: PCの故障・誤削除により、蓄積したレース結果・特徴量・予測ログ・パドック評価が失われる可能性がある。
- **方針**: 個人利用のスコープでは、自動バックアップ機能を本ツールで実装するのはオーバースペックと判断する。利用者の判断で、必要に応じて`data/*.db`を別ドライブやクラウドストレージへ定期的に手動コピーする運用でカバーする（JRA-VANデータの二次配布制限があるため、コピー先も個人管理下に限定すること。`07_セキュリティ設計.md`§4参照）。
- 自動バックアップの仕組みが必要と判断された場合は、別途要件定義を行う。
