## 2. 新規テーブルの設計方針（提案・未実装）

### 2.1 past_performances

`models.PastPerformance`データクラスのフィールドとそのまま対応する。既存の`db.py`のSQLスタイル（`CREATE TABLE IF NOT EXISTS`、複合PK）に合わせる。

```sql
CREATE TABLE IF NOT EXISTS past_performances (
    horse_name TEXT NOT NULL,
    race_date TEXT NOT NULL,
    finish_position INTEGER NOT NULL,
    distance INTEGER NOT NULL,
    time_seconds REAL NOT NULL,
    last_3f_seconds REAL NOT NULL,
    race_class TEXT NOT NULL,
    track_condition TEXT NOT NULL,
    PRIMARY KEY (horse_name, race_date)
);
```

- PKは`(horse_name, race_date)`とし、`models.py`のデータクラスは変更不要。
- `horse_name`を仮キーとして使う制約については3.2を参照。

### 2.2 jockey_trainer_stats

現行の`models.JockeyTrainerStats`（`name`, `win_rate`のみ）には無い`as_of_date`列を追加する必要がある。

```sql
CREATE TABLE IF NOT EXISTS jockey_trainer_stats (
    role TEXT NOT NULL CHECK (role IN ('jockey', 'trainer')),
    name TEXT NOT NULL,
    as_of_date TEXT NOT NULL,
    win_rate REAL NOT NULL,
    PRIMARY KEY (role, name, as_of_date)
);
```

**なぜas_of_dateが必要か**: 騎手・調教師の勝率は日々更新される。M8バックテストで過去のレースにスコアリングを適用する際、「現在の」勝率ではなく「そのレース開催時点の」勝率を使わないと、未来の情報が過去の予測に混入する（リーク）。これは`demo_data.py`で past_performance の生成方法を見直した際（結果生成用の乱数と過去成績生成用の乱数を分離）と同種の問題であり、実データ運用前に対応が必要。

**設計判断**: `models.JockeyTrainerStats`データクラス自体は変更せず（既存コードへの影響を避けるため）、`db.py`側の保存・読込関数が`as_of_date`を明示的な引数として受け取る方針とする。

## 4. 既知の制約・今後の課題

- **外部キー制約が効いていない**: `db.py`の`connect()`は`PRAGMA foreign_keys = ON`を実行しているが、現行の`CREATE TABLE`文には1つも`FOREIGN KEY`句が定義されていない。そのため参照整合性は実質保証されていない。`entries.race_id → races.race_id`、`body_weights/odds/paddock_manual_scores/race_results.(race_id, horse_number) → entries.(race_id, horse_number)`のFK追加を今後の課題とする。
- **`horse_name`が仮キー**: 実際のJV-Dataには血統登録番号という一意なIDが存在するが、現行のモックデータ・提案スキーマは馬名を実質的な主キーとして扱っている。同名馬（年度またぎ・地方競馬との重複等）が存在した場合に破綻するリスクがあるため、`JVLinkDataSource`実装時（要件定義書12.3-d）に血統登録番号ベースへの移行を検討する。
